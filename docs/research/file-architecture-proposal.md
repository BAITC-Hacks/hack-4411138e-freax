# Предлагаемая структура файлов AYQYN

23 сентября 2026. Предложение после просмотра локальных импортов, входных страниц, сервера и CLI. Файлы приложения не перемещались. Текущий план исправления качества продолжается; массовый перенос одновременно с ним не предлагается.

## Выбор

Один Python-пакет `ayqyn`, отдельный `web`, существующие `scripts`, `tests` и `docs`. Без перехода на другой веб-фреймворк, React, микросервисы или отдельную векторную БД. Структура соответствует уже существующим обязанностям модулей.

```text
hackalem/
├── server.py                   # тонкая совместимая точка запуска
├── ayqyn/
│   ├── __init__.py
│   ├── paths.py                # единые пути проекта, web, результатов и кеша
│   ├── documents/
│   │   ├── __init__.py
│   │   ├── docx.py             # parse_docx и его вспомогательные функции
│   │   ├── pdf.py              # pdf_input.py
│   │   ├── packets.py          # пакет, роли документов, версии
│   │   ├── store.py            # document_store.py: адреса, контекст, охват
│   │   └── text.py             # общая нормализация, без вызовов моделей
│   ├── retrieval/
│   │   ├── __init__.py
│   │   └── hybrid.py           # hybrid_search.py: чанки, индексы, RRF
│   ├── agent/
│   │   ├── __init__.py
│   │   ├── runner.py           # research_agent.py
│   │   ├── tools.py            # research_tools.py: схемы и исполнение
│   │   ├── state.py            # research_state.py: состояние и проверки сдачи
│   │   ├── context.py          # research_context.py
│   │   ├── inventory.py        # research_inventory.py
│   │   └── metrics.py          # research_metrics.py

│   │   ├── __init__.py

│   │   ├── functions.py        # function_analysis.py
│   │   └── batch.py            # существующий совместимый пакетный сценарий
│   ├── providers/
│   │   ├── __init__.py
│   │   ├── llm.py              # пока перенос целиком, без переписывания
│   │   └── embeddings.py       # embeddings.py, включая обращения к провайдеру
│   ├── storage/
│   │   ├── __init__.py

│   └── http/
│       ├── __init__.py
│       ├── server.py           # текущий обработчик и запуск сервера
│       └── workspace.py        # research_workspace.py: представление для UI
├── web/
│   ├── analyze.html            # основной анализ комплекта
│   ├── index.html              # отдельный существующий практикум
│   ├── *.js                   # первый перенос: все JS целиком, имена прежние
│   ├── *.css                  # первый перенос: CSS целиком, порядок прежний
│   ├── assets/
```

`datasets/` — целевое место, а не команда сейчас переместить пользовательские материалы. Сначала нужно проверить все ссылки CLI, тестов и документов. Синтетические наборы, реальные источники и эталоны должны различаться; эталоны нельзя индексировать как входные документы агента. Копии материалов не удалять автоматически.

## Почему именно так

- `documents` знает, что прочитано и откуда взят текст; не зависит от управляющего агента или LLM-анализатора.
- `retrieval` возвращает кандидатов с source ID. Не принимает решения о потере, передаче или конфликте.
- `agent` выбирает инструменты, ведёт исследование и формулирует выводы. Проверка существования цитаты не объявляется смысловой проверкой.
- `analysis` сохраняет действующие правила и отдельный сценарий анализа функций. Нельзя объявлять их ненужными и удалять: сервер и CLI пока используют эти пути.
- `providers` концентрирует сетевые обращения и настройки моделей. Существующий `llm.py` смешивает транспорт и операции сравнения; сначала переносим его без изменения поведения. Разделять транспорт и предметные запросы стоит отдельной небольшой правкой позже.
- `http/workspace.py` преобразует исследование в ответ интерфейсу; логика агента не должна зависеть от браузерного представления.
- `paths.py` исключает изменение каталога результатов при переносе файла: сейчас `server.py` и другие модули вычисляют корень через собственный `__file__`.

Нормализацию из `function_analysis.normalized`, которую сейчас использует `document_store.py`, перенести в `documents/text.py`, сохранив точное поведение. Это устраняет зависимость хранилища источников от LLM-анализатора. Не нужно превращать этот файл в общий `utils.py` для всего проекта.

## Правила зависимостей

```text
HTTP / CLI → агент и существующие режимы анализа
агент → документы + поиск + провайдеры + хранение прогонов
поиск → документы + провайдер эмбеддингов
документы → обработка файлов и текста
браузер → HTTP API
```

Обратных импортов из документов в агент/HTTP быть не должно. Не создавать новые абстрактные репозитории, контейнер внедрения зависимостей или интерфейсы для каждого файла ради структуры. `hybrid.py` не дробить на пять файлов, пока это не упрощает конкретную работу.

## Фронтенд: сначала физическое отделение

Сейчас `analyze.html` использует `analysis.js`, `research-client.js`, оформление AYQYN и общие ресурсы; `index.html` использует другой сценарий с `app.js` и `cases.js`. Это две существующие страницы, а не доказанные дубликаты. `sources.js` и `demo-sources.js` могут быть нужны демонстрационному пути — их нельзя удалять по имени.

Первым шагом достаточно собрать HTML/CSS/JS/assets/vendor под `web/`, сохранив относительные ссылки и публичные URL. Это уже убирает фронтенд из корня. Раскладывать далее по `pages/`, `shared/` и `styles/` можно отдельно после проверки браузерных импортов; сейчас это добавит много замен без выигрыша качества.

Сервер должен раздавать разрешённые ресурсы из `WEB_ROOT`, а не открыть статическую раздачу всего проекта. Документы из `sources/` обслуживаются отдельным существующим разрешённым маршрутом. `.env`, исходники сервера, эталоны и журналы не становятся публичными после переноса.

## Порядок миграции

1. **Зафиксировать рабочую точку.** Завершить текущие изменения агента, сохранить результат R8/R9 и согласовать отсутствие параллельных правок переносимых файлов. Зафиксировать тестовую команду и состояние файлов.
2. **Отделить web.** Перенести браузерные файлы, изменить статический корень и разрешённые пути. Публичные URL и порядок подключения сохранить. Проверить обе страницы и сценарий загрузка → результат → источник → экспорт.
3. **Перенести Python-модули группами.** Сначала пути/хранение/провайдеры, затем документы/анализ/поиск, затем агент и HTTP. Обновлять импорты, CLI и тестовые monkeypatch-пути в каждой группе. Все каталоги Python — обычные пакеты с `__init__.py`.
4. **Разделить `analyzer.py` узко.** Перенести парсинг в `documents/docx.py`, правила в `analysis/rules.py`; общие чистые функции вынести только если действительно используются обеими частями. Эту операцию не смешивать с улучшением парсинга.
5. **Сохранить точки входа.** Корневой `server.py` — короткий вызов серверного `main`; `scripts/run_research.py` и `scripts/run_analysis.py` продолжают работать прежними командами. Не требуется сразу переходить на `src/` и установку пакета.
6. **Обновить карту и ссылки.** README и REVIEW_HANDOFF описывают актуальные команды и архитектуру; старые отчёты остаются историческими. Пользовательские наборы перемещать последними, отдельно от кода.

После каждой группы — затронутые тесты; перед завершением — полный существующий набор и проверка браузерного сценария. Платный повтор модели не нужен для каждой операции переноса: сначала тестовый драйвер и сохранённые артефакты. Если поведение анализа изменилось, это отдельная задача, не результат файлового рефакторинга.

## Приёмка переноса

- Прежняя команда запуска сервера и оба CLI работают.
- Источники сохраняют прежние ID, цитаты и доступность; старый результат открывается и исследование возобновляется из прежнего каталога.
- Подготовка пакета, поиск и агент с тестовым драйвером дают те же содержательные результаты при одинаковых входах.
- Обе страницы загружаются; нет сломанных ресурсов или импортов, источник и экспорт доступны.
- Секреты, журналы и gold set не доступны через статический маршрут.
- Нет двух расходящихся реализаций одного модуля. Если временно нужен совместимый импорт, это только короткий реэкспорт с обозначенным сроком удаления.

Эта структура упрощает сопровождение. Она сама по себе не исправляет качество retrieval или выводов и не заменяет приёмку R8/R9.
