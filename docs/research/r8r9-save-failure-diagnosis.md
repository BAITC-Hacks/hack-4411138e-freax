# Почему найденные изменения не попали в итог: воспроизведение без API

23 сентября 2026. Исследован сохранённый R8/R9-прогон `r-a30fd364034e4c50a5953840e45e3844`. Код приложения и файлы прогона не изменены. Проверки выполнены в памяти на текущем локальном коде, без сети и без `state.save()`. Параллельные правки команды означают, что текущий код отличается от кода исходного запуска.

## Доказанный механизм

На шагах 2–3 агент прочитал новый 5.3 (`after:p159`) и старый 5.3 (`before:p150`) с контекстом. На шаге 4 он попытался сохранить две записи:

- `r-53-owner-change`: наблюдение об изменении владельцев группы функций; цитаты заголовков включены.
- `r-53-monitoring-expanded`: изменение мониторинга, связанное с G10; процитированы старый 5.3.6 (`before:p164`) и новый 5.3.7 (`after:p178`), но заголовки владельцев не включены в доказательства этой записи.

Владелец есть в прочитанном контексте, но не в индивидуальном `before_evidence`/`after_evidence` второй записи. Валидатор отклоняет её. `save_checked_results` и внешний `update_research_state` работают атомарно: вместе с неверно оформленной записью откатывается и другая запись.

Следующая независимая блокировка: тот же вызов пытается закрыть `t73` как `checked`, хотя требования охвата группы не выполнены. Даже исправление доказательств не спасает результаты, пока закрытие группы входит в общую транзакцию.

## Локальный эксперимент

Загружены `ResearchState` и `DocumentStore` из сохранённых файлов. В `read_ids` включены только фрагменты, возвращённые чтением до шага 4. Для воспроизведения использованы фактические аргументы шага 4; результаты хранились исключительно в памяти.

| Проверка | Результат текущего валидатора |
|---|---|
| Первая запись отдельно, без изменений | Принята |
| Вторая запись отдельно, без изменений | Отклонена: нет дословного названия владельца в доказательствах обеих сторон |
| Вторая запись с добавленными заголовками из доказательств первой | Принята |
| Обе записи с исправленным evidence плюс исходное закрытие t73 | Отклонено закрытие задачи; сохранённых записей 0 |
| Те же исправленные записи без обновления задачи | Приняты; сохранены оба result ID |

Принятие означает прохождение проверок источников и контракта, а не независимую смысловую приёмку. Первая запись слишком обобщена для замены отдельных эталонных функций. Вторая содержит релевантное G10 изменение, но итоговый текст ещё должен сохранять ограничения эталона: появление формулировки в этом пункте не доказывает, что мониторинга раньше не существовало вообще.

## Дополнительные ошибки в журнале

1. На шаге 11 ошибка закрытия `t20` снова отменяет результат. На шаге 15 вновь отсутствуют заголовки в отдельных функциональных записях. Агент не исправляет адресно одну ошибку и переключается между темами.
2. На шаге 15 обязанность **выявлять** недостаточное или дублирующее покрытие названа доказательством дублирования. Это смысловая ошибка: обязанность искать риск не подтверждает его наличие. Отклонять такой вывод правильно.
3. На шаге 21 сохранены две записи, но обе не являются завершёнными проверками функций: одна `insufficient_data`, другая структурная `partial/added_to_list`.
4. На шаге 22 эти две записи переданы и напрямую в `findings`, и через `saved_result_ids`. Тогда итог содержал четыре записи. В текущем коде уже появилась проверка дубликатов в `ResearchState.submit`; старое утверждение «дубли никак не проверяются» больше неактуально. Но `ResearchTools` по-прежнему добавляет сохранённые записи к новым, поэтому повтор может превратиться в отказ всей сдачи вместо корректного объединения.
5. Сообщения о нескольких отдельных результатах обозначаются одинаковым `finding: 1`, потому что каждый проверяется одиночным вызовом. Без `result_id` модель получает неоднозначную обратную связь.

## Лекарство: три локальных изменения

### 1. Собрать доказательства конкретной функции

Для каждого результата обеспечить два разных основания: текст действия/объекта и текст явного владельца. Заголовок может быть отдельным источником той же стороны. В инструментальном ответе показывать доступные явные родительские заголовки и их source ID; не выводить владельца из произвольного соседнего пункта.

Минимальный шаг — исправлять конкретную запись: дополнить её evidence уже прочитанным заголовком. Следующий устойчивый шаг — структурное поле источника владельца с проверкой связи через `parent_id`. Одна только похожесть названий или нахождение в одном документе такой связи не доказывает. Не отключать проверку владельцев целиком.

### 2. Разделить сохранение результатов и закрытие задачи

Независимые корректные результаты должны переживать ошибку закрытия группы. Предлагаемый контракт ответа:

```text
accepted_result_ids: [...]
rejected_results: [{result_id, field, code, required_evidence}]
task_update_errors: [{task_id, missing_candidate_ids, open_questions}]
```

Сохранение атомарно внутри одной записи; независимые записи проверяются отдельно. Закрытие группы отдельно проверяет собственный охват и не откатывает уже принятый результат. Если результаты взаимозависимы, не принимать недоказанное утверждение лишь ради частичного успеха.

Агенту нужно исправлять отклонённые ID, а не пересобирать весь пакет и переключаться на новую тему. Чтение всех подпунктов не приравнивается к проверке всех функций; состояние группы `partial` нормально при наличии нескольких готовых наблюдений.

### 3. Сделать сдачу устойчивой к повтору сохранённой записи

Предпочтительный путь — сдавать сохранённые результаты по ID. Если одновременно пришла полностью идентичная новая запись, включать её один раз и сообщать о повторе. При различающихся версиях одной записи возвращать адресную ошибку, не выбирать произвольно. Разные действия одного пункта, этапы и условия не объединять по сходству текста.

Нельзя ограничиваться запретом дублей: запрет уже появился, но без исправления объединения может снова съесть последний доступный шаг агента.

## Проверки до следующего платного запуска

- Повторить фактический шаг 4: запись без источника владельца получает ошибку со своим result ID; другая корректная запись не теряется.
- Добавление прочитанного явного заголовка устраняет именно ошибку evidence; неподтверждённый департамент по-прежнему отклоняется.
- Неверное закрытие t73 оставляет её незавершённой, но не удаляет корректные сохранённые результаты.
- Повторная отправка принятого result ID не создаёт вторую запись.
- Сохранённая запись плюс её точная копия в новых выводах дают один результат; конфликтующие версии не сливаются молча.
- «Обязан выявлять дублирование» не принимается как установленное дублирование; требуется два назначения одной операции с сопоставимыми исполнителями, этапами и условиями.
- Через тестовый driver воспроизвести цепочку: ошибка evidence → адресное исправление → сохранение → сокращение истории → сдача по ID. Без модели можно проверить поведение системы; способность живого агента выбрать правильное исправление этим не доказана.

## Что это не объясняет

Диагностика доказывает потерю уже найденных и частично сформулированных наблюдений, но не доказывает качество поиска по всем G01–G15. G09/G11 требуют корректного сопоставления функций, G12 — исследования другого раздела. После устранения блокировок нужно оценивать весь набор; обещать 5/5 по этому воспроизведению нельзя.

Порядок: исправить сохранение и адресность ошибок → проверить офлайн-сценарии → только затем следующий сопоставимый живой прогон. Query rewriting, реранкер и файловый рефакторинг не устраняют доказанную причину этого сбоя.
