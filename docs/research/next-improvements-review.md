## Как отделить проблему поиска от проблемы анализа

Для каждой пропущенной функции записать цепочку:

1. Нужный текст есть после парсинга, включая владельца и продолжения?
2. Соответствующий источник попал в первые k результатов поиска?
3. Агент действительно открыл его и необходимый родительский контекст?
4. Агент сформулировал правильное наблюдение?
5. Оно сохранилось после сокращения памяти и прошло сдачу?

Если источник найден, прочитан и правильно понят, а сдача его блокирует, изменение эмбеддингов проблему не решает. Если source отсутствует после парсинга, реранкер также не поможет.

Подготовить небольшой фиксированный набор поисковых запросов к G01–G15: исходная формулировка, естественный пересказ, запрос без имени прежнего владельца. Сравнить BM25, dense и hybrid на одинаковых k и фильтрах. Регистрировать попадание нужного пункта, наличие обеих сторон сопоставления и доступность контекста владельца. Это отладочный набор; ответы эталона не передавать агенту. Он уже использовался при разработке и не является независимой проверкой обобщения.

Реранкер имеет смысл испытывать только если нужные источники регулярно есть среди кандидатов, но не проходят в короткую выдачу. При отсутствии источника в наборе кандидатов сначала проверяются запрос, фильтры, извлечение и разбиение текста.

## Сохранённые идеи на следующий этап

- **OCR/VLM по конкретной необходимости.** Не только для полностью сканированной страницы: изображение таблицы или штампа может быть внутри PDF с хорошим текстовым слоем. Возвращать страницу/область, извлечённый текст и ограничение качества; не принимать предполагаемого владельца по расположению без проверки. Подключать после базовой приёмки, если тестовый вход демонстрирует такую потерю.
- **Версии документов с основаниями.** Дата файла и номер редакции помогают, но не заменяют дату действия и основание замены. Автоматическая классификация плюс исправление пользователем; отдельный ручной режим «до/после» сохраняется.
- **Таблицы и ответственность.** Вместе с ячейкой хранить заголовки строки/столбца и адрес таблицы. Не назначать владельца по специализации подразделения. Для БВА оставлять БВА.
- **Не удалять одинаковый текст разных источников.** Это могут быть разные назначения ответственности. Объединять повторную выдачу одного source ID, сохраняя разные документы и контекст.
- **Дополнительные функции ТЗ.** Сопоставление с предоставленными нормами, сравнение с другими операторами и рекомендации перераспределения — после основного сценария. Для рекомендаций отдельно показывать исходные назначения, обнаруженное пересечение и предположения; не выдавать предлагаемую структуру за факт.

## Приёмка следующей итерации

1. Все 15 эталонных функций оценены, а не только удачные примеры. Для G08–G12 отдельно проверены содержательные изменения; для G06/G13 — переформулировки.
2. Для каждого существенного вывода отдельно отвечено: «источник существует?» и «достаточно ли он обосновывает вывод?». Нет неподтверждённых владельцев, исключительных передач или создания подразделения по одному новому названию.
3. Сохранённый правильный результат переживает сокращение истории и сдаётся по ID без обязательного повторного чтения. Исправления можно проследить по журналу.
4. Измерены токены, время, повторные чтения и число корректных результатов при сопоставимых модели, настройках и бюджете. Уменьшение токенов при потере полезных результатов не считается улучшением качества.
5. Выполнен сценарий загрузка → агент → источники → экспорт. Неизвестные роли и неполный охват видны в результате. Контрольный комплект жюри остаётся непроверенным.

Порог 2/5 содержательных изменений годится лишь как промежуточный сигнал восстановления, но не как заявление о завершении приёмки. Цель R8/R9 — все пять контрольных содержательных изменений без ложных переносов; оставшиеся несовпадения должны быть перечислены явно.
