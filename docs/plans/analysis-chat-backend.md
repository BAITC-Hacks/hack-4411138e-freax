# План: чат-агент по завершённому анализу

Статус: бэкенд реализован; технические проверки пройдены. Живая смысловая приёмка требует настроенного провайдера.
Дата: 2026-09-23. Реализация основана на c287a1e, ветка codex/backend-research-snapshot. При последней проверке upstream этой ветки не изменился; новый frontend origin/main 38f0281 интегрируется в отдельной задаче.
Ответственность этой работы: Python-бэкенд, агент, API и проверки. Фронтенд делает другой участник.

## Сценарий и границы

Пользователь проводит сверку документов, видит результат анализа сверху страницы, затем прокручивает ниже к чату и задаёт вопросы об этом анализе. Чат относится к конкретному результату и его комплекту документов. Размещение блока, прокрутка, поле ввода и отображение сообщений — задача фронтенда.

Примеры вопросов: «Почему это признано потерей?», «Где это написано?», «Кому передана функция?», «А это не разные стадии согласования?», «Какие выводы пока не подтверждены?», «Сформулируй краткий итог».

Первый выпуск отвечает, объясняет и перепроверяет по тем же источникам. Если обнаружена ошибка первоначального анализа, ответ прямо указывает расхождение и доказательства. Исходный отчёт и решения аналитика автоматически не изменяются. Новые документы требуют нового анализа; интернет-поиск, редактирование отчёта из чата, голос и дополнительные форматы — отдельные задачи.

Статическое демо C010 не становится выполненным анализом. Реальный прогон синтетических документов, напротив, может иметь чат с сохранением пометки synthetic.

## Снимок и адреса источников

Снимок создаётся сервером из реально выполненного анализа, а не из присланного клиентом произвольного отчёта. Хранятся исходный результат, документы и извлечённые фрагменты, SHA-256, роли, происхождение findings, предупреждения, версия схемы и контрольная сумма снимка. Версия кода и параметры живых запросов фиксируются существующим RunRecord для каждого обращения модели. Путь: output/analyses/a-<uuid>/; каталог output уже исключён из Git.

Результат сохраняется и в режиме rules/fallback, без требования API-ключа и без автоматического вызова embeddings. При ошибке сохранения существующий результат анализа остаётся доступен, но analysis_id отсутствует и причина недоступности чата возвращается явно. Ответ needs_review не создаёт доступный чат.

Адреса текущих путей различаются: в старой паре pN повторяется между before/after; в пакете используются dN:pM; в исследовании — d-<sha256>:pN. Нужен адаптер без повторного разбора и без изменения ID в прежнем ответе. Для пары канонический ID включает сторону; в остальных путях сохраняются уникальные ID. Таблица соответствия хранит исходный ID, сторону, документ и SHA-256, включая связи заголовков/соседей/таблиц. Не вызывать combine_documents повторно: он меняет ID на месте.

Результаты исследовательского API пока имеют другую схему findings. Адаптер сохраняет исходную схему и назначает стабильные ID внутри снимка; не выдумывает соответствия с находками старого API. Общий/дублирующийся документ не становится двумя независимыми доказательствами.

Изменение файлов, ролей или повторный анализ создаёт новый analysis_id. История прежнего чата остаётся привязана к старому снимку. Для импортируемого исследовательского результата в MVP допустимы completed и insufficient_data с явными ограничениями; незавершённые исследования не выдаются за готовый анализ.

## Поведение агента

1. Начать с вопроса, компактного обзора анализа, релевантной истории и явно выбранных находок. Текст отчёта — прежний вывод, текст документа — первичный источник.
2. По вопросу выбрать поиск и чтение нужных фрагментов, соседей, владельцев и противоположной редакции. Не отправлять весь комплект и весь журнал на каждом шаге.
3. При оспаривании вывода искать подтверждения и опровержения. Не считать пустой поиск доказательством потери; указывать фактический охват и неполноту комплекта.
4. Вернуть ответ через finish_answer с утверждениями и ссылками. Сервер проверяет принадлежность источника анализу, факт чтения, точность цитаты, документ и сторону. Не прошедшую проверку цитату нельзя отдать пользователю как подтверждение.
5. При неоднозначном «это» задать уточнение. При недостатке источников ограничить ответ. При сбое модели вернуть ошибку операции, без выдуманного ответа по правилам.

Инструменты чата: get_analysis_summary, get_finding, list_documents, search, read_context, get_coverage, finish_answer. Инструменты submit_findings и изменения исходного ResearchState не предоставлять. История может ссылаться на прошлые цитаты, но не превращается в новый первичный источник; для фактического утверждения контекст должен быть доступен в текущем ходе.

Чтение и бюджет чата не изменяют coverage, findings и журнал первоначального исследования. Совместно используется неизменяемый корпус/совместимый индекс; query-usage и журнал каждого ответа сохраняются отдельно. При несовместимости кеша не переписывать индекс исходного исследования.

В MVP установлен ограниченный бюджет на ответ: до 6 вызовов модели, 10 инструментов и 60 секунд на подготовку и ответ вместе. Пределы следует уточнить по живой проверке. История хранится полностью (до 100 вопросов); в модель передаётся недавняя часть в пределах 24 000 символов, без обрезки отдельных сообщений и без выдуманного резюме. Общий контекст ограничен 160 000 символами. Усечение и незавершённая проверка отражаются в ограничениях ответа.

## Сохранение, ошибки и область доступа

Один диалог на analysis_id в MVP. Атомарное сохранение снимка, истории и состояния каждого ответа; отдельные имена временных файлов или сериализация записи. Один активный ответ на анализ, ограничение общего числа фоновых работ. Повтор client_message_id не создаёт новый платный вызов.

После перезапуска незавершённые ходы становятся interrupted; автоматического повторного списания нет. Новая попытка имеет новый client_message_id. Ключи живут только в окружении/памяти запроса; конфигурации с секретом нет в снимках, истории, ошибках и журналах. Проверку привязки серверного ключа к адресу провайдера сохранить.

Существующие ограничения Host/Origin и выдачи файлов сохранить. Случайный ID не считается многопользовательской авторизацией: MVP остаётся локальным. Все инструменты ограничены текущим снимком; инструкции внутри документов, прошлых ответов и найденных фрагментов не меняют правила агента. Работа с произвольными путями, URL и чужими анализами не предоставляется.

| Проверка | Ожидаемый результат |

| «А эта функция есть у другого отдела?» | Поиск альтернативного владельца; подтверждённое расхождение со старым анализом явно показано |

## Передача фронтенду

Порядок подключения: получить analysis_id из настоящего результата → загрузить историю → отправить сообщение → опрашивать turn → показать ответ и проверенные источники. Блок чата располагается под анализом по задаче фронтенда. Наши артефакты: API, примеры JSON/ошибок, тестовый сценарий и описание ограничений. HTML/CSS/analysis.js в эту работу не входят.

До первого запуска фронтенд может показать «Для чата выполните анализ». Недоступный провайдер, подготовка индекса, обработка, уточнение, недостаток данных и ошибка — разные серверные состояния, не фиктивный прогресс. Оценки аналитика на клиенте не считаются синхронизированными; чат об этом сообщает при соответствующем вопросе.

## Как обновлять после каждого pull

По просьбе пользователя сделать pull сначала проверить status и refs, сохранить изменения команды и объединить ветки без переписывания общей истории. После объединения сравнить старый и новый HEAD: server.py, analysis/packet/research модули, модели данных, тесты и контракт фронтенда.

Обновить в этом файле базовый коммит, фактическое состояние, статусы P0–P5, зависимости и критерии приёмки. Если другая ветка уже реализовала часть задачи, проверить её и отметить выполненную часть вместо повторной реализации. При изменении контрактов синхронно править проект API и README-ссылку при необходимости. Прошедшие проверки отмечать с датой; неподтверждённое оставлять неподтверждённым.

Добавлять запись в журнал: какие коммиты пришли, что поменялось для чата, что теперь следующий шаг. Если пришли только не относящиеся к чату изменения, записать это и оставить порядок работ. Обновление плана не означает разрешения начать реализацию или делать push.
