# Osnovanie Synthetic OrgDiff RU v1.0

Готовый небольшой контрольный набор для прототипа анализа организационных изменений.
10 сценариев, 40 одностраничных PDF на русском языке с извлекаемым текстом.
В каждом сценарии два комплекта: before и after; в каждом оргструктура и функциональное положение.
Это удобная организация тестовых данных, а не требование интерфейса о четырех обязательных полях.

## Быстрый запуск демо
1. Распакуйте архив.
2. Загрузите оба PDF из inputs/C010/before в комплект «До».
3. Загрузите оба PDF из inputs/C010/after в комплект «После».
4. Запустите реальный анализ и сравните с annotations/expected_results.json, запись C010.
5. Проверьте, что каждый вывод открывает правильный PDF, страницу 1 и указанный пункт.
6. Для разработки фронтенда используйте frontend/mock_analysis_C010.json. Пометьте такой режим «Демо-данные».

Не загружайте весь архив или файлы разных сценариев в один анализ.
JSON рядом с PDF - альтернативное структурированное представление того же документа для разработки,
не дополнительный документ: не подавайте PDF и его JSON как два независимых источника.
Входные PDF не содержат правильных ответов. Эталонные ответы не передавать анализатору.
Формат JSON предложен для этого набора и может потребовать адаптации к API вашей команды.

## Сценарии
- C001: Без изменений.
- C002: Переименование и перенумерация.
- C003: Передача функции существующему подразделению.
- C004: Потенциальная потеря функции.
- C005: Дублирование ответственности.
- C006: Самопроверка закупок.
- C007: Разделение подразделения.
- C008: Похожие функции с разными объектами.
- C009: Неполный комплект после.
- C010: Смешанный демонстрационный сценарий.

## Что проверять
- C001/C002/C003/C008: отсутствие ложных потерь, конфликтов и дублирования согласно forbidden_types.
- C004: потенциальная потеря после проверки ВСЕХ документов after, а не только найденных фрагментов.
- C005: дублирование подтверждают два разных назначения одной обязанности.
- C006: конфликт подтвержден обязанностями и явным запретом самопроверки в п. 2.6.
- C007: разделение и передача функций; новый самостоятельный отдел отделять от правопреемников.
- C009: недостаточно данных. Не объявлять потерю по отсутствующему разделу.
- C010: смешанный сценарий для демонстрации всех основных вкладок интерфейса.

Положительные разметки являются целевыми проверками, а не исчерпывающей инвентаризацией
всех сохраненных функций. Разрешены дополнительные корректные выводы с источниками.
Для потери нет «цитаты отсутствия»: evidence содержит исходную обязанность, search_scope -
весь проверяемый комплект after. Указывайте отсутствие только в предоставленном комплекте.
forbidden_types действует на весь сценарий; новые типы результатов согласуйте с разметкой вручную.

## Оценка
Считайте полноту целевых находок отдельно по типам, число ложных тревог в контрольных сценариях
и долю выводов с корректными источниками (документ, пункт, точная цитата).
Совпадение метки без правильного подразделения/функции и доказательств не засчитывается.
Потеря засчитывается только с проверкой всего after и оговоркой о предоставленном комплекте.
Автоматическая структурная проверка набора не является проверкой качества вашей модели.

## Происхождение и ограничения
Все документы и разметка созданы синтетически для этого задания, не скопированы из реальных положений.
«АО Учебная сеть» - вымышленная организация. Это НЕ внутренние документы Казахтелекома.
Разметка подготовлена автором генератора, независимую экспертную проверку не проходила.
Набор для отладки и демонстрации, а не репрезентативный benchmark и не достаточный корпус для обучения.
Не заявляйте промышленную точность на основании этих 10 коротких примеров.
Нет сканов/OCR, сложных таблиц, Excel/DOCX, многостраничных приложений и юридической оценки.
Переход к реальной оценке: дополните исходными редакциями организатора и ручной разметкой команды.
Держите будущие контрольные реальные документы отдельно от примеров, на которых настраиваете промпт.
Внешние источники перечислены в sources.json; их файлы не включены и их лицензии не переназначены.
